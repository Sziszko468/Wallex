# Languages (i18n)

WALLEX speaks **English** and **Hungarian**. The user picks the language in the account menu,
on the Settings screen (web and mobile) and on the sign-in / registration screens. The choice is
remembered on the device and saved to the account (`User.language`), so it follows the user to
every device.

## How a language is chosen

1. At start-up: the language saved on this device → else the browser / phone language → else English.
2. After signing in, **the account's language wins** (it is what the other devices use too).
3. Changing it saves it to the account (`PATCH /api/auth/me/ {"language": "hu"}`). If saving fails
   the choice still holds on this device.
4. Every API request carries `Accept-Language`, so the server answers in the same language
   (validation messages and every text it writes).

## Where the texts live

| App | Catalogs | Library |
|---|---|---|
| Web | `web/src/i18n/locales/{en,hu}/*.ts` | `i18next` + `react-i18next` |
| Mobile | `mobile/i18n/locales/{en,hu}/*.ts` | `i18next` + `react-i18next` + `expo-localization` |

`en` is the source of truth. The Hungarian catalog is typed against it (`DeepStrings<typeof en>`),
and `t("…")` is typed too, so a missing or misspelled key is a compile error. Tests additionally
check that both languages have the same keys and `{{placeholders}}`, that every plural form
(`_one` / `_other`) exists, that nothing is left in English in the Hungarian catalog, and that no
key is unused.

## Rules for code

- **No text in code.** Components use `const { t } = useTranslation()`; modules that are not
  components use `import { t } from "i18next"`. The product name is the one exception:
  `APP_NAME` (`config/app.ts`).
- **No string-building around translations.** Use interpolation (`{{name}}`), plurals
  (`count` with `key_one` / `key_other`) and `<Trans>` for text with markup. Word order differs
  between languages.
- **Numbers, money and dates** go through `utils/format.ts`, which follows the interface language
  (`1 234,50 Ft` vs `HUF 1,234`). Never call `toLocaleString(undefined)`.
- Texts the **server** writes (insights, notifications, achievements…) are translated there; the
  clients just display them and reload them when the language changes.
- Web: changing the language remounts everything below `LanguageProvider`, so every view reloads
  its data. Mobile keeps its navigation state; texts re-render through `useTranslation` and every
  `useAsyncData` revalidates.

## The server (Django)

Everything the API writes for a person goes through Django's `gettext`; the English sentence is
the `msgid` and `backend/locale/hu/LC_MESSAGES/django.po` holds the Hungarian.

- **Which language answers a request:** `LocaleMiddleware` reads `Accept-Language` (`hu`, `hu-HU`,
  `hu-HU,en;q=0.5`…); anything else is English. The response says `Content-Language` and
  `Vary: Accept-Language`. Error `code`s and every field name never change with the language.
- **Texts written outside a request** (a notification created by the scheduled job, a push sent
  after a transaction was saved) use the **account's** language, not the request's:
  `apps/common/i18n.py` → `language_of(user)` / `@in_user_language`.
- **Whole sentences, named placeholders.** `_("Spending was %(percent)s%% higher than in %(month)s.") % {…}`
  — never `"Spending was " + x`, never f-strings around a translated word; counts use
  `ngettext`. `%` is written `%%`. Month and weekday names come from Django's own catalog.
- **Money in texts** is formatted for the reader (`apps/currencies/formatting.py`:
  `€1,234.50` vs `1 234,50 €`).
- **Category names:** the ten default categories are stored in English (rules and CSV import match
  on that) and shown translated (`apps/categories/defaults.py` → `display_name`); a category the
  user created is shown exactly as typed. The category API lists the defaults in the request's
  language, and refuses a new category whose name is a default's translated name.
- **Achievements:** the catalog lives in the database in English; `achievement_texts.py` lists the
  names and descriptions once so `makemessages` can see them.
- The `.mo` files are compiled from the `.po` files and **not kept in git**: the production image
  compiles them (`msgfmt --check`), `docker compose up` runs `compilemessages`, and the test suite
  compiles them before the first test. They need GNU gettext (`msgfmt`), which the Docker image has.

Tests: `backend/tests/test_translation_catalog.py` reads the source and the `.po` and fails when a
text in the code has no translation, when the catalog has leftovers, when an entry is empty/fuzzy
or still English, or when a placeholder / `%%` differs between the two languages.
`backend/tests/test_i18n.py` covers what the endpoints do with it.

## Adding a language

1. Add the code to `SUPPORTED_LANGUAGES`, `LANGUAGE_NAMES` and `INTL_LOCALES` in `i18n/languages.ts` (web and mobile).
2. Copy the `en` catalog folder, translate it, and register it in `locales/index.ts`.
3. Add the code to `LANGUAGES` in `backend/config/settings/base.py` (it feeds the `User.language` choices),
   run `python manage.py makemessages -l <code> -i .venv`, translate `locale/<code>/LC_MESSAGES/django.po`,
   and give `apps/currencies/formatting.py` the number format of the language.
4. Run the tests: the catalog tests list everything that is missing.

## Adding a text

**Web / mobile**

1. Add the key to `en/<feature>.ts`, then to `hu/<feature>.ts` (the compiler tells you if you forget).
2. Use it: `t("feature.key", { name })`.

**Server**

1. Write it with `gettext` (`_`, `ngettext`; `gettext_lazy` at import time or in serializers).
   Import it by its real name or as `_` — `makemessages` doesn't find other aliases.
2. Run `python manage.py makemessages -l hu --no-obsolete -i .venv` and translate the new entry.
3. `python manage.py compilemessages -i .venv` (or just restart the dev container). The catalog
   test names anything you forgot.
